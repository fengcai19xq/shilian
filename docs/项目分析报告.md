## 一、项目概况

航锂智能体是一个企业级知识智能体平台，核心能力包括：
- 多部门文档统一入库（Java ingest 服务，支持 RAGFlow / WeKnora 双底座）
- 按权限的问答与引用溯源（Python retrieval-proxy + decide + gateway）
- 融资清单自动成册（Java matcher + packager，三态匹配确认）
- 企微组织架构同步与统一身份（Java wecom-sync，OIDC + 企微）

**技术栈**：
- Python 薄层服务：FastAPI + Pydantic（6 个模块，94 个 .py 文件）
- Java 业务后端：Spring Boot 3.x + Maven（4 个模块，200 个 .java 文件）
- 前端：React 18 + Vite 5 + TypeScript 5.5（26 个 .tsx + 14 个 .ts）
- 部署：Docker Compose（机房单机测试环境）

## 三、已完成优化（本次提交）

### 1. CI 矩阵补齐 matcher 和 packager Python 模块

**问题**：`.github/workflows/ci.yml` 的 Python 测试矩阵只包含 `retrieval-proxy, gateway, decide, bff`，遗漏了 `matcher` 和 `packager` 两个 Python 服务模块。这两个模块有独立的 `pyproject.toml` 和测试套件（matcher 43 项、packager 27 项测试），但不在 CI 覆盖范围内，回归无保障。

**修复**：在 CI 矩阵中补充 `matcher` 和 `packager`。

**文件**：`.github/workflows/ci.yml` 第 15 行

### 2. Spring Boot 版本统一

**问题**：`services-java/packager/pom.xml` 使用 Spring Boot **3.5.16**，而其余三个模块（ingest/matcher/wecom-sync）使用 **3.3.5**。版本不一致导致：
- 同一部署环境中 Spring 自动配置行为可能不一致
- 传递依赖版本可能冲突（如 spring-security、jackson）
- 维护认知负担增加

**修复**：将 packager 的 Spring Boot 版本从 3.5.16 降为 3.3.5，与全仓统一。

**文件**：`services-java/packager/pom.xml` 第 10 行

### 3. PDFBox / POI 依赖版本统一

**问题**：
- packager 使用 `pdfbox 3.0.8` + `poi 5.5.1`
- ingest 使用 `pdfbox 3.0.3` + `poi 5.2.5`
- matcher 使用 `poi 5.2.5`

三个模块使用了不同版本的 Apache PDFBox 和 Apache POI，如果未来同 JVM 部署或共享代码，会产生类路径冲突。

**修复**：统一全部为 `pdfbox 3.0.8` + `poi 5.5.1`（取较新稳定版本）。

**文件**：
- `services-java/ingest/pom.xml`（pdfbox 3.0.3→3.0.8, poi 5.2.5→5.5.1）
- `services-java/matcher/pom.xml`（poi 5.2.5→5.5.1）

### 4. 添加 .dockerignore

**问题**：项目根目录无 `.dockerignore`，Docker 构建上下文会包含全部文件（包括 `spike/` 诊断脚本、`docs/`、`scripts/`、git 历史、IDE 配置等），导致构建上下文体积膨胀、构建变慢。

**修复**：新增 `.dockerignore`，排除：
- 编译产物（`*.pyc`, `*.class`, `target/`, `node_modules/`）
- 本地数据目录（`audit/`, `usage/`, `ingest-data/`, `filestore/`, `packages/`, `matcher-data/`）
- spike 诊断脚本（`.gitignore` 中已排除的文件同步排除）
- 非运行时文件（`docs/`, `scripts/`, `tasks.json`, `README.md`, `AGENTS.md`）

**文件**：`.dockerignore`（新增）

## 四、优化建议（未实施，需后续排期）

### 架构层面

#### 1. KbEncoding 四处重复实现应抽取为共享包

**现状**：KB 编码逻辑（`kb_name` / `parse_kb_name` / `visible_kbs`）在四处重复实现：
- `services/retrieval-proxy/src/retrieval_proxy/kb_encoding.py`（Python，生产）
- `spike/weknora/kb_encoding.py`（Python，spike）
- `services-java/ingest/src/main/java/com/shilian/ingest/ragflow/KbEncoding.java`（Java）
- `services-java/wecom-sync/src/main/java/com/shilian/wecomsync/weknora/KbEncoding.java`（Java）

四处实现需逐字对齐，任何一处修改都需同步另外三处，且各有独立测试"钉死"。

**建议**：
- Python 侧：retrieval-proxy 的 `kb_encoding.py` 已是生产实现，spike 侧应直接 import 它而非维护副本
- Java 侧：抽取为独立 Maven 模块 `shilian-common`，ingest 和 wecom-sync 共同依赖
- 长期：考虑用 JSON Schema 或 Protobuf 定义 KB 编码规则，多语言生成

#### 2. Python matcher/packager 与 Java matcher/packager 并存

**现状**：matcher 和 packager 都有 Python 原版（`services/matcher/`, `services/packager/`）和 Java 重写版（`services-java/matcher/`, `services-java/packager/`）。Java 版是验收基准（Python 测试逐条移植为 JUnit），但 Python 版仍在 CI 中运行。

**建议**：
- 明确 Python 版的定位：如果仅为 Java 重写的参考实现，应在 README 中标注「legacy/reference only」并考虑归档
- 如果两版都需要维护，应建立测试等价性回归机制（同一 manifest 输入，两侧产物字节一致）

#### 3. ObjectStorage 桩需明确路由保护

**现状**：`services/packager/src/packager/storage.py` 的 `ObjectStorage` 三个方法全部抛 `NotImplementedError`。Java 侧 `services-java/packager/.../ObjectStorage.java` 同样。如果配置错误导致生产环境选中 `ObjectStorage`，会直接抛异常。

**建议**：在 `StorageConfig` / `Storage` 工厂中加启动时断言：如果 `storage_type=oss` 但未配置 OSS 凭据，fail-fast 并给出明确错误信息，而非运行时才抛 `NotImplementedError`。

### 工程层面

#### 4. Python 服务缺少 ruff lint 在 CI 中执行

**现状**：各 Python 模块的 `pyproject.toml` 声明了 `ruff>=0.4` 作为开发依赖，但 CI 只执行 `python -m pytest -q`，不执行 ruff lint。

**建议**：在 CI 的 Python job 中增加 `ruff check src/ tests/` 步骤，确保代码风格一致性。

#### 5. Java 模块缺少 spring-boot-starter-validation（matcher/packager）

**现状**：matcher 和 packager 的 `pom.xml` 未声明 `spring-boot-starter-validation`（ingest 和 wecom-sync 有）。当前不影响功能（源码未使用 `@Valid` 等注解），但未来添加校验注解时会遗漏。

**建议**：统一四个模块都声明 `spring-boot-starter-validation`，或在需要时再添加。低优先级。

#### 6. wecom-sync 的 WeKnora 空间成员端点未现场核对

**现状**：`HttpWeknoraIdentityClient.findMember()` 和离职移除端点抛 `UnsupportedOperationException("空间成员端点待现场核对")`。`membersEnabled` 默认 `false`。

**建议**：在 WK13 或后续现场验证中核对 WeKnora 的成员管理 API，确认后移除桩并启用 `membersEnabled=true`。

#### 7. spike 目录诊断脚本过多

**现状**：`spike/weknora/` 下有约 20 个诊断/修复脚本（`diag_*.py`, `check_*.py`, `fix_*.py`, `find_timeout.py`, `extract_*.py` 等），已在 `.gitignore` 中排除（不入库）。但 `verify_live.py`（19.3KB）和 `kb_encoding.py`（5.9KB）等入库脚本与生产代码有重复。

**建议**：spike 验证完成后，将 `verify_live.py` 的测试断言迁移到正式测试套件（`services/retrieval-proxy/tests/`），spike 目录保留文档（DESIGN-REVIEW.md / SPIKE-REPORT.md）作为决策记录。

### 安全层面

#### 8. BFF_DEV_MODE 生产必须关闭

**现状**：`docker-compose.yml` 中 `BFF_DEV_MODE` 默认 `false`，但 `BFF_DEV_PRINCIPAL` 提供了一个固定主体。如果误开 dev mode，所有请求将以该固定主体身份执行，绕过身份验证。

**建议**：在 BFF 启动时检查：如果 `BFF_DEV_MODE=true` 且非测试环境（如检测到生产端口或环境变量），fail-fast 并打印警告。

#### 9. 前端 KB_SCOPE 硬编码

**现状**：`web/src/state/useWorkbench.ts` 第 26 行 `KB_SCOPE = ['kb_finance', 'kb_audit']` 硬编码。虽然 BFF 会覆盖浏览器传入的 kb_scope（T20 安全加固），但前端硬编码值仍可能导致混淆。

**建议**：前端不维护 KB_SCOPE 常量，改为从 BFF 响应中动态获取可用知识库列表，或直接由 BFF 注入。

剩余未完成任务大多受限于非代码资源（业务方数据、额度、现场环境），代码层面可继续推进的主要是 WK15（MCP Server）和 WK18（成册闭环，需 contracts 签字）。
